# Testing

Our approach to testing will change as the project progresses.
In the beginning we focus more on change than on test.

The backend is tested with [Kotest](https://kotest.io/) from the `kbackend`
directory. There are two kinds of tests, both described in more detail in the
[kbackend README](../kbackend/README.md#testing).

## Unit and repository tests

```bash
./gradlew test
```

These test the logic of the backend, including the repositories that access the
database. Repository and job tests use Testcontainers for PostgreSQL, so Docker
must be running. They seed their own data.

## API tests

As the API generated by PostgREST cannot be unit-tested, and the key to the
success of the project is to have a good API, it makes sense to test thoroughly
the API from the outside, _i.e._, through HTTP calls.

```bash
./gradlew apiTest
```

The API tests start the backend in-process on top of real PostgreSQL and
PostgREST containers, with the database created by the Liquibase migrations.
There is one test class per API resource, and the tests chain several calls to
the API, which makes it possible to test full scenarios involving several
different API calls, and not only single endpoints.

Our tests are made to be as independent as possible from each other, and to use
new data when possible, instead of interacting with existing data. Each test
class truncates the tables it touches before running its tests, and tests seed
the data they need.

## RLS coverage

RLS policies are documented in the database code with `-- RLS: <ID>` comments,
and the API tests that cover a policy include a `// RLS: <ID>` comment. To list
the policies that are covered and those that are not, run:

```bash
just coverage
```

## Frontend testing

Frontend tests use Vitest for unit tests and Playwright for end-to-end screenshot
tests. See [Frontend testing](testing-frontend.md) for setup and commands.
